## Goal

Close the finding the predecessor record reported and explicitly declined to fix: Pixel Launcher
draws a light-blue ring (`#B0D9FF`) around the PRism adaptive icon on Android 13+ because the icon has
no `<monochrome>` layer for the OS's "Themed icons" feature to use. Add that layer, generated
deterministically from the existing source artwork — not a hand-made file — so Themed Icons renders a
real tinted silhouette instead of falling back to an undecorated backplate.

## Pre-flight technical check — is the silhouette derivation ambiguous?

Checked before committing to this scope, per the task's explicit stop condition. **It is not
ambiguous.** Measured luminance values, sampled directly from `prism-logo-source.png` (not assumed):

| Region | Luminance | Sample |
| --- | --- | --- |
| Background | ~3–5 | `#020304`, `#030305` |
| Interior shaded facets (darkest to brightest) | ~44–52 | `#2A2D30` … `#323538` |
| Red beam (the darkest beam colour) | ~82–90 | `#D42022` |
| Blue beam | ~93–108 | `#0071FF` |
| Cyan beam | ~132–153 | `#02BBF8` |
| Green beam | ~145–161 | `#4AC641` |
| Orange beam | ~171–174 (edges dip to ~69) | `#FDA501` |
| Shield outline / white beam | ~253 | `#FCFDFF` |

There is a clean, comfortable gap — no overlap in any sample taken — between "background and
interior facets" (≤52) and "every beam colour plus the outline" (≥82, aside from a few naturally
antialiased edge pixels). A threshold anywhere in roughly 55–80 separates the same two groups
identically. This is the same *kind* of decision `scripts/alpha-key.py` already makes (a measured
luminance threshold with a soft ramp for antialiasing) — mirrored, not invented fresh: keep bright
pixels opaque instead of keeping dark pixels transparent.

**What this produces:** a silhouette of the shield's outline and the full beam fan, with the
interior diamond shading and background dropped. This is consistent with Android's own guidance for
monochrome/themed icons — "a simple, single-colour representation," not a shaded miniature of the
full-colour icon — and it is the outline that has always been described as the mark's "dominant
subject" in every prior brand sprint.

## Tasks and success criteria

1. **Generate the monochrome derivative.** `scripts/generate-app-icons.sh` (or a new small Python
   helper alongside `alpha-key.py`) emits a fourth file from the same crop already used for the other
   three. Success: regenerating from the committed source produces byte-identical output — the same
   reproducibility bar every prior derivative met.
2. **Add and document.** File lands in `assets/brand/`; `assets/brand/README.md`'s layout table and
   wiring section are updated to describe it, matching the existing entries' format.
3. **Wire into Android config.** `app.json`'s `android.adaptiveIcon` gains `monochromeImage`.
   Success: `expo prebuild --platform android` produces a `mipmap-anydpi-v26/ic_launcher.xml` with a
   real `<monochrome>` element (not absent, as it is today) referencing a real generated resource.
4. **On-device verification, both states.** Same rigor as the predecessor record: screenshots plus
   named pixel samples, not a single glance.
   - **Themed icons ON:** the ring is gone; the icon renders as a single-colour tinted silhouette.
   - **Themed icons OFF:** the icon renders exactly as the predecessor record already confirmed —
     full colour, unclipped, no regression.
5. **iOS spot check.** Confirm the iOS icon is visually unchanged (expected, since `expo.icon` is not
   touched by this sprint).
